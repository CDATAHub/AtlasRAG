## User Scenarios & Testing *(mandatory)*

### User Story 1 - 复杂问题按计划拆解执行，回答带引用 (Priority: P1)

业务人员提出一个复杂问题（含多个子任务，如「这款重疾险的等待期多久？等待期内出险赔吗？」），
系统先产出可观测的执行计划——把问题拆成子任务并改写检索式，然后按计划逐步调用检索工具
收集证据，最后基于全部证据生成带引用的答案。业务人员在前端运行记录中能看到
「规划 → 逐条工具调用 → 证据 → 回答」的完整决策过程，理解答案是怎么来的。

**Why this priority**: 这是阶段 2 的核心升级——从「检索前置的固定流水线」变为「可规划的
检索编排」（章程原则 I）；单程跑通即是最小可用 MVP，其余故事都叠加在它之上。

**Independent Test**: 在已入库条款库上提出含两个子任务的问题，系统产出 ≥ 2 步计划并逐条
执行，最终答案同时回应两个子问题且每个结论带可展开原文的引用。

**Acceptance Scenarios**:

1. **Given** 条款库已含相关条款, **When** 提出含两个子任务的问题,
   **Then** 系统产出可观测的执行计划（≥ 2 个步骤），逐步执行后答案同时回应两个子问题
2. **Given** 任一非拒答回答, **When** 业务人员点开引用标记,
   **Then** 可见条款原文（文档名、条款编号、被引原句），原句支撑答案结论（继承阶段 1 口径）
3. **Given** 寒暄或常识类提问（「你好」「保险是什么」）, **When** 系统接收提问,
   **Then** 走快速路径直接回应，不发起条款检索，首字节明显快于条款问答
4. **Given** 无需检索即可回应的提问, **When** 规划判定直接回答,
   **Then** 运行档案中工具调用次数为 0

---

### User Story 2 - 证据不足时反思回环，重规划只替换未执行步骤 (Priority: P1)

首轮检索并生成草稿后，系统评估证据是否充分回答问题；不充分时自动改写检索式、补充检索或
更换工具再试。重规划保留已执行步骤与已获证据、只替换未执行部分（不重复已完成的检索）。
回环最多 3 轮（含首轮），之后无论如何强制收敛：能答则答，不能答则明确「资料不足」。

**Why this priority**: 「可反思」是效果提升的主要来源——修复首轮漏检（阶段 1 抽样评测中
约 1/3 问题首轮未命中）；与 US1 同为回答质量的直接构成。

**Independent Test**: 用同配置首轮评测中未命中的失败案例提问，观察到第二轮改写检索式
后命中正确条款并正确作答；再构造一个持续无命中的问题，确认 3 轮内停止并输出「资料不足」。

**Acceptance Scenarios**:

1. **Given** 首轮检索未命中而换一种问法可命中, **When** 反思判定证据不足,
   **Then** 系统自动改写检索式补检索，最终答案命中正确条款
2. **Given** 发生重规划, **When** 检查执行过程,
   **Then** 已执行步骤与已获证据被保留，未重复执行已完成的检索
3. **Given** 反思回环已达上限（3 轮）仍证据不足, **When** 系统收敛,
   **Then** 输出「资料不足」与改进提问建议，绝不编造条款内容（继承阶段 1 拒答口径）

---

### User Story 3 - 必收敛三重保险：任何输入都有限步停止 (Priority: P2)

无论输入多么古怪——超长、持续无命中、诱导反复检索——系统都在步数上限、熔断超时、
token 预算三重保险的约束下确定性停止，并输出可用结果或明确的「资料不足」；触发保险时
给出降级输出而非空白或半截答案。每次结束都说明收敛原因。

**Why this priority**: 章程原则 IV 的红线（NON-NEGOTIABLE），但作为独立切片它加固
US1/US2 的循环而非阻塞其价值；与阶段 1 的拒答路径同级别处理。

**Independent Test**: 构造一组对抗性输入（超长问题、诱导循环的问题、持续无命中问题），
逐一提交，全部在明确上限内返回确定性结果，无无限等待、无半截答案。

**Acceptance Scenarios**:

1. **Given** 一个诱导反复检索的问题, **When** 循环达到步数上限（默认 6 步）,
   **Then** 系统强制收敛并输出当前最优可用结果或「资料不足」
2. **Given** 链路执行缓慢, **When** 达到熔断超时（20 秒）,
   **Then** 系统立即停止循环并输出降级结果与明确提示，不编造
3. **Given** 某轮对话 token 消耗持续攀升, **When** 达到 token 预算上限（默认 8000，含推理 token）,
   **Then** 系统停止循环并输出可用结果，运行档案记录实际用量
4. **Given** 任一次问答结束, **When** 检查结束事件,
   **Then** 携带收敛原因（自然收敛 / 步数上限 / 超时 / 预算 / 拒答）

### User Story 4 - 多轮对话与会话管理 (Priority: P2)

用户在同一会话中连续追问（首轮问「A 产品的等待期多久」，追问「那它的宽限期呢」），系统
结合会话历史理解指代与省略并正确作答。会话可查询历史、可删除；历史过长时自动压缩对话
过程但保留已引用的证据与结论；同一会话串行执行，重复提交幂等。

**Why this priority**: 真实使用是多轮的，但单轮闭环须先立住；多轮是在状态机之上的叠加，
依赖 US1/US2 就绪。

**Independent Test**: 新建会话提问 A 产品等待期，随后追问「它的宽限期呢」，追问的回答
正确指向 A 产品的宽限期条款且带引用；查询会话历史可见两轮完整问答。

**Acceptance Scenarios**:

1. **Given** 会话中已有首轮问答, **When** 用户追问「它的宽限期呢」,
   **Then** 系统结合上下文解析指代，回答引用该产品的宽限期条款
2. **Given** 一个已存在的会话, **When** 客户端查询会话历史,
   **Then** 返回此前全部问答（含引用），按时间有序
3. **Given** 同一会话已有进行中的请求, **When** 再次提交提问,
   **Then** 返回明确的冲突提示，MUST NOT 产生交错回答
4. **Given** 相同会话与客户端消息标识的重复提交, **When** 系统处理,
   **Then** 幂等返回既有结果，不重复生成与计费
5. **Given** 会话历史超过压缩阈值, **When** 继续对话,
   **Then** 系统压缩对话过程但保留已引用的证据与结论，答案引用仍可展开为条款原文
6. **Given** 用户请求删除自己的会话, **When** 删除完成,
   **Then** 该会话不可再查询；跨租户访问他人会话 MUST 得到「不存在」而非泄露存在性

---

### User Story 5 - 检查点恢复：进程重启后续跑 (Priority: P3)

循环执行中的状态被持久化保存；服务进程重启或崩溃后，进行中的会话能从最后一个成功节点
续跑，已完成的检索不重复执行，也不输出半截答案。检查点不可用时给出明确重试指引。

**Why this priority**: 生产可靠性与「可恢复」设计目标的体现（docs/03 设计目标 4）；不
阻塞核心问答价值，属阶段 2 收尾能力。

**Independent Test**: 在循环执行中重启服务进程，恢复后对同一会话重新请求，系统能续跑完成
问答且不重复已执行步骤；删除检查点后重复实验，得到明确错误与重试指引而非半截答案。

**Acceptance Scenarios**:

1. **Given** 循环执行中进程重启, **When** 客户端带相同会话与消息标识重新请求,
   **Then** 系统从检查点续跑同一次回答，已完成的检索步骤不重复执行
2. **Given** 检查点损坏或丢失, **When** 客户端带相同标识重新请求,
   **Then** 系统返回明确错误与重新开始指引，MUST NOT 输出半截答案

---

### Edge Cases

- 规划输出格式异常（不可解析）→ 重试后仍失败则降级为「单步检索 + 生成」保底路径，不中断服务
- 全部工具调用失败（检索层故障）→ 明确「服务暂不可用」提示，绝不编造条款内容
- 用户在流式输出中断开连接 → 循环终止、档案记录中断，会话保留已完成部分
- 超长问题 → 长度校验拒绝并提示；不因超长输入耗尽预算
- 提问中夹带指令试图绕过租户边界 → 身份与租户过滤只来自令牌与 DAO 强制注入，模型指令不改变权限
- 反思判定「证据充分」但引用为空 → 按拒答处理（宁可少答不可错答）
- 会话并发与幂等重放同时发生 → 串行化优先，重放请求得到一致结果
- 删除会话时有进行中的请求 → 请求完成后删除生效，不产生悬挂状态

## Requirements *(mandatory)*

### Functional Requirements

**循环与规划**

- **FR-001**: 系统 MUST 在回答条款类问题前产出可观测的执行计划（子任务列表 + 改写后的
  检索式），并按计划逐步调度执行
- **FR-002**: 检索 MUST 以工具调用形式被规划与调度；模型可见工具面 MUST 收敛为「条款检索」
  与「文档读取」两类（章程 I），内部检索路径 MUST NOT 单独暴露给模型
- **FR-003**: 寒暄/常识类提问 MUST 走快速路径直接回应，不消耗条款检索与完整规划
- **FR-004**: 工具调用失败 MUST NOT 中断循环：失败记入证据池并标记，由反思决定换工具、
  换检索式重试或放弃
- **FR-005**: 草稿生成后 MUST 进行证据充分性评估；不足时 MUST 重规划，重规划 MUST 保留
  已执行步骤与已获证据、只替换未执行步骤
- **FR-006**: 反思回环（含首轮）MUST 最多 3 轮，达到上限后 MUST 强制收敛输出

**收敛保险**

- **FR-007**: 循环 MUST 具备三重收敛保险——步数上限（默认 6 步）、熔断超时（20 秒触发
  降级输出）、token 预算（默认 8000，含推理 token）；任一触发 MUST 确定性停止并输出
  可用结果或「资料不足」
- **FR-008**: 证据不足或回环耗尽时 MUST 走拒答路径并给出改进提问建议（继承阶段 1）；
  降级输出 MUST NOT 编造条款内容

**多轮与会话**

- **FR-009**: 客户端 MUST 可在问答请求中携带会话标识；缺省时系统创建新会话并在响应中返回
- **FR-010**: 系统 MUST 提供会话历史查询与删除接口；历史含问答原文与引用；删除后会话
  MUST 不可再查询
- **FR-011**: 多轮提问 MUST 能结合会话历史解析指代与省略（如「它的宽限期呢」）
- **FR-012**: 同一会话 MUST 串行执行：已有进行中请求时，新请求 MUST 得到明确的冲突提示
- **FR-013**: 相同会话标识 + 客户端消息标识的重复请求 MUST 幂等：不重复生成、不重复计费
- **FR-014**: 会话历史超过阈值时 MUST 压缩对话过程，但 MUST 保留已引用的证据与结论
  （证据链不压缩）

**可观测与治理**

- **FR-015**: 问答事件流 MUST 覆盖完整循环：规划、工具调用、证据、回答增量、引用、结束；
  结束事件 MUST 携带收敛原因（自然收敛 / 步数上限 / 超时 / 预算 / 拒答）
- **FR-016**: 运行档案（阶段 1 最小档案）MUST 扩展记录：计划轮数、步数、token 用量、
  收敛原因；MUST NOT 在本阶段引入完整可观测平台
- **FR-017**: 所有接口 MUST 校验 JWT，租户身份 MUST 只来自令牌 claims；会话与检索 MUST
  按租户隔离，跨租户资源 MUST 不可见（继承章程 V）
- **FR-018**: 循环状态 MUST 持久化为检查点；进程重启后，客户端带相同会话与消息标识重新
  请求时，系统 MUST 从检查点续跑被中断的那次回答并继续输出剩余结果（已完成步骤不重做），
  MUST NOT 输出半截答案或丢弃已执行的检索重答一遍

### Key Entities *(include if feature involves data)*

- **会话（Session）**：租户内一次多轮对话的容器；标识、归属租户、创建/更新时间、状态、
  过期时间（第一版仅预留字段，自动清理阶段 5 启用）；包含有序消息列表
- **消息（Message）**：会话中的一条提问或回答；角色、内容、引用列表；回答消息关联运行档案
- **执行计划（Plan）**：规划产出的有序子任务列表；每步含动作、工具、检索式、理由；
  重规划时保留已执行部分、只替换未执行部分
- **证据与引用**：继承阶段 1（条款块原文、来源、相关度分数）；三者包含关系：
  工具原始返回 ⊇ 进入生成的证据 ⊇ 答案实际引用
- **运行档案（Runtime Log）**：阶段 1 最小档案的扩展——新增计划轮数、步数、token 用量、
  收敛原因

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 质量不回退——闭卷评测集上，AgentLoop 链路的检索命中指标不低于阶段 1 基线
  （按基线 ±2σ 门禁口径判定，章程 II）
- **SC-002**: 回环修复——在验收配置（含 rerank）的首轮未命中失败集中，≥ 30% 经反思
  回环补检索后转为命中；分母 = 同配置首轮失败数（2026-09-04 澄清），不依赖阶段 1 旧报告
- **SC-003**: 必收敛——100 条对抗性输入（超长、歧义、持续无命中、诱导循环）100% 在
  步数/超时/预算上限内确定性停止；零无限循环、零半截答案
- **SC-004**: 复杂问题（L1/L3 难度）端到端总时长 95% ≤ 30 秒；熔断触发时降级输出及时到达
- **SC-005**: 寒暄/常识类提问首字节 95% < 1 秒
- **SC-006**: 多轮指代消解——50 条双轮测试对话中 ≥ 90% 的追问正确解析指代并命中正确条款
- **SC-007**: 证据链保真——开启上下文压缩的长会话中，抽检 20 条答案引用 100% 可展开为
  条款原文且与答案结论一致
- **SC-008**: 恢复——演示进程重启后至少 1 个进行中会话成功续跑，已完成检索步骤不重复执行
- **SC-009**: L0 延迟不劣化——引入规划后，L0 简单事实题端到端总时长不劣于阶段 1 基线
  （±2σ 口径）；8s 目标不在本阶段验收（2026-09-04 澄清）

## Assumptions

- 实现遵循章程技术栈约束：以状态机方式实现循环（LangGraph），检查点以数据库持久化以满足
  「进程重启续跑」验收（docs/03 §3.7）
- 本阶段实际实现的工具只有条款检索一类；文档读取工具（doc_reader）仅定义接口契约
  不实现（2026-09-04 澄清），阶段 3 随 Tool Registry / 执行引擎（权限、校验、并行、
  幂等中间件，章程 III）一并落地；工具接口按契约设计以便阶段 3 平滑替换
- 会话存储沿用现有 PostgreSQL；过期时间字段从第一版预留但自动清理不实现（2026-09-04
  澄清）；留存删除细化（软删→物理删、审计 hash chain）属阶段 5，本阶段会话删除仅为软删
