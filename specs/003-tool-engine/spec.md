## User Scenarios & Testing *(mandatory)*

### User Story 1 - 执行引擎：一次工具调用自带全部健壮性保障 (Priority: P1)

作为运维/开发同学，我希望任何一次工具调用（无论内置还是外部来源）都自动经过统一的执行管道——参数校验、超时控制、可重试错误的退避重试、异常的统一包装与恢复——而不是依赖每个工具自己写对这些逻辑。这样单个工具的作者只需关心业务逻辑，健壮性由中间件一次做对（章程 III）。

**Why this priority**: 执行引擎是阶段 3 验收的主体（docs/09 四项验收之二），也是后续所有工具（含 MCP 外部工具）的运行底座；US2~US5 都在它之上扩展。

**Independent Test**: 用 mock 工具注入各类故障（慢响应、瞬时网络错误、非法参数、未知工具名），断言每次调用都在契约声明的上限内返回结构化结果（成功或分类明确的失败），且失败仅产生 failed 标记证据、不中断 Agent 循环。

**Acceptance Scenarios**:

1. **Given** 一个声明了超时上限的工具且其实现挂起不返回，**When** Agent 按计划调用它，**Then** 调用在超时上限内以结构化超时错误结束，失败记入证据（failed 标记），循环按既有收敛规则继续
2. **Given** 一个实现存在瞬时故障（首次失败、重试即成功）的工具，**When** 该故障发生，**Then** 引擎按指数退避自动重试并在重试上限内成功，调用方拿到正常结果且能看到重试次数
3. **Given** 一次带非法参数的工具调用，**When** 引擎执行参数校验，**Then** 调用在进入工具实现前被拦截，返回结构化校验错误，不产生半执行副作用
4. **Given** 一个非幂等工具在执行中超时（副作用状态未知），**When** 引擎考虑重试，**Then** 引擎 MUST NOT 重发该调用，仅记录失败并交由上层决策（查询确认或放弃）
5. **Given** 工具实现抛出任意未预期异常，**When** 引擎捕获，**Then** 异常被包装为携带工具名、重试次数、耗时、追踪标识的结构化错误写入证据，循环不中断

---

### User Story 2 - 权限收敛：模型只见、只调它有权的工具 (Priority: P1)

作为多租户场景下的平台管理员，我希望每个请求的工具可见面由该请求实际持有的权限域（scopes）驱动：无权工具不出现在规划提示里，越权调用在执行前被结构化拒绝。这样权限从源头收敛（章程 I/V），而不是事后拦截。

**Why this priority**: scope 收敛是阶段 3 验收四项之一（docs/09），且属安全属性（章程 V）；当前可见面是硬编码的单一权限域，需演进为请求级驱动。

**Independent Test**: 构造持有不同 scopes 的请求（含空 scopes），断言规划面只含授权工具；对未授权工具直接发起调用，断言被结构化拒绝且无任何工具实现被执行。

**Acceptance Scenarios**:

1. **Given** 一个只持有「检索读」权限域的请求，**When** 规划节点生成工具面，**Then** 面内只含所需权限域为其子集的工具，其余工具不可见
2. **Given** 一次试图调用请求权限域之外工具的调用，**When** 引擎执行权限校验，**Then** 调用在工具实现执行前被结构化拒绝，错误进入证据（failed 标记），循环不中断
3. **Given** 某请求持有空权限域列表，**When** 生成规划面，**Then** 工具面为空，Agent 按既有「无工具可用」路径降级（不崩溃、不编造）

### User Story 3 - doc_reader 兑现：按文档/章节精读条款原文 (Priority: P2)

作为提问的用户，当检索命中的父块摘要不足以回答细节问题时，我希望 Agent 能用文档读取工具按 doc_id/章节编号精读条款原文，让答案基于完整原文而非片段。

**Why this priority**: doc_reader 契约已在阶段 2 先行定义（保证工具面措辞稳定），本阶段兑现实现；直接提升回答质量，且验证执行引擎对第二类内置工具的通用性。

**Independent Test**: 对已入库文档按 doc_id 与 (doc_id, sec_no) 两种方式调用，断言返回章节结构与原文一致；跨租户访问被过滤。

**Acceptance Scenarios**:

1. **Given** 已入库的条款文档，**When** 以 doc_id 调用 doc_reader，**Then** 返回该文档全部章节（编号/标题/原文文本）
2. **Given** 已入库的条款文档，**When** 以 (doc_id, sec_no) 调用，**Then** 只返回指定章节的原文
3. **Given** 属于其他租户的文档，**When** 调用 doc_reader，**Then** 返回找不到，不泄漏其他租户内容（密级过滤随阶段 5 统一落地，clarify Q3）

---

### User Story 4 - 并行执行：同一步的独立调用同时跑 (Priority: P2)

作为用户，我希望同一计划步内多个相互独立的工具调用并行执行、结果稳定合并，从而缩短多调用场景的等待时间；不可并行的调用（如写操作）保持串行避免竞态。

**Why this priority**: 并行是执行引擎验收清单的组成部分（docs/09），收益是延迟，但依赖 US1 管道先就位。

**Independent Test**: 用时延受控的 mock 工具构造「一步两调用」场景，断言墙钟耗时显著小于串行、结果顺序与计划一致、部分失败不影响其余调用。

**Acceptance Scenarios**:

1. **Given** 一个计划步包含 2 个相互独立且可并行的调用，**When** 引擎执行该步，**Then** 两调用并发执行，总耗时不超过单调用耗时的 1.5 倍，结果按计划顺序合并
2. **Given** 一个计划步包含 2 个调用且其一标记为不可并行，**When** 引擎执行该步，**Then** 该调用与前序调用串行执行，不产生并发竞态
3. **Given** 并行执行中一个调用失败，**When** 其余调用正常完成，**Then** 成功结果照常进入证据，失败调用单独标记 failed，循环不中断且其余调用不被连带取消

---

### User Story 5 - MCP 接入：外部工具与内置工具统一调度 (Priority: P2)

作为平台开发者，我希望通过 MCP 客户端把外部 MCP Server 提供的工具动态注册进同一注册表（统一命名、契约自动生成），与内置工具被同一个模型工具面规划、被同一执行管道治理；MCP 来源故障不拖垮内置工具。

**Why this priority**: 「接入 ≥1 个 MCP Server 工具」是阶段 3 验收硬性项（docs/09）与 JD 关键词；依赖 US1 管道与 US2 权限模型先定型。

**Independent Test**: 启动本地最小 MCP Server（演示工具），断言其工具出现在注册表并经模型工具面被规划调用；用 in-process mock session 复现「Server 不可达/超时」与「清单含非法 schema」，断言降级行为（章程 VII）。

**Acceptance Scenarios**:

1. **Given** 一个运行中的 MCP Server 提供若干工具，**When** 客户端完成发现与注册，**Then** 这些工具以隔离命名空间进入注册表，契约（描述与参数 schema）由 Server 清单自动生成，无需手工维护
2. **Given** 已注册的 MCP 工具在授权范围内，**When** 模型规划并调用它，**Then** 调用经与内置工具完全相同的执行管道（权限/校验/超时/重试口径一致）完成
3. **Given** MCP Server 在启动或调用时不可达/超时，**When** 系统运行，**Then** 该来源工具降级为不可见或标记失败，内置工具的调用成功率不受影响
4. **Given** MCP Server 清单中的工具与内置工具重名，**When** 注册，**Then** 命名空间隔离保证两者互不覆盖

---

### Edge Cases

- 工具契约未声明执行策略元数据 → 引擎采用保守默认（最小超时、不重试、视为幂等读）并记录告警
- 重试次数耗尽 → 与单次失败同构处理：结构化失败进证据，交反思决策（换工具/换关键词/降级），不中断
- 非幂等工具超时后副作用状态未知 → 仅允许后续查询确认，禁止盲目重发（章程 III）
- MCP 工具清单返回非法/不完整 schema → 该工具跳过注册并告警，其余工具正常注册
- 同一计划步并行调用全部失败 → 按既有收敛规则进入反思/降级路径，输出完整降级答案而非半截结果
- 权限域为空但模型仍试图产出工具调用 → 结构化拒绝（同越权路径），不执行任何实现
- 请求携带的 scopes 与工具所需权限域部分重叠 → 仅当所需权限域完全被覆盖时可见/可调，部分覆盖视为无权
- doc_reader 请求的 sec_no 在目标文档中不存在 → 返回结构化「章节不存在」，不回退为全文（避免静默扩大上下文）

## Requirements *(mandatory)*

### Functional Requirements

**契约与注册**

- **FR-001**: 每个工具契约 MUST 声明执行策略元数据：超时上限、最大重试次数、是否幂等、是否可并行、所需权限域（scope）；缺省时系统 MUST 应用保守默认值
- **FR-002**: 内置工具与 MCP 外部工具 MUST 注册进同一注册表统一发现与调度；MCP 工具 MUST 使用隔离命名空间（前缀），禁止覆盖内置工具
- **FR-003**: 模型可见工具面 MUST 由当前请求持有的权限域驱动收敛：仅当工具所需权限域完全被请求权限域覆盖时可见；无权工具 MUST NOT 出现在规划提示中

**执行管道**

- **FR-004**: 执行引擎 MUST 按固定顺序施加中间件：权限校验 → 参数校验 → 幂等判断 → 执行（并行/串行）→ 超时控制 → 重试 → 异常恢复；健壮性逻辑 MUST NOT 散落在单个工具实现内（章程 III）
- **FR-005**: 参数校验 MUST 在进入工具实现前拦截非法参数，返回结构化校验错误，不产生半执行副作用
- **FR-006**: 每个工具调用 MUST 受其契约超时上限约束；超时 MUST 返回结构化超时错误并交上层决策（反思/降级），MUST NOT 中断 Agent 循环
- **FR-007**: 重试 MUST 仅针对可重试错误（网络抖动、超时、5xx 类瞬时故障）且采用退避策略；不可重试错误（参数非法、权限拒绝、4xx 类）MUST 直接失败不浪费重试
- **FR-008**: 非幂等工具 MUST NOT 被自动重试；超时后副作用状态未知时 MUST 只允许查询确认（章程 III）
- **FR-009**: 写类工具（非幂等）接入时 MUST 支持幂等键：同一幂等键的重复提交 MUST 返回首次执行结果而不重复产生副作用（v1 工具面全为读工具，见 Assumptions）
- **FR-010**: 工具异常 MUST 统一包装为携带工具名、错误分类、重试次数、耗时、追踪标识的结构化错误，写入证据并标记 failed；失败 MUST NOT 中断 Agent 循环（延续 002 FR-004 口径）

**并行**

- **FR-011**: 计划步 MUST 支持可选多调用列表（缺省单调用，与既有单调用计划向后兼容，clarify Q1）；步内相互独立且标记可并行的调用 MUST 并行执行、结果按计划顺序合并；标记不可并行的调用 MUST 串行执行；并行中单个失败 MUST NOT 连带取消其余调用

**工具实现**

- **FR-012**: doc_reader MUST 实现按 doc_id（全文分章）与 (doc_id, sec_no)（指定章节）读取条款原文，并强制租户过滤（与既有检索口径一致，clarify Q3；密级过滤随阶段 5 租户隔离统一落地）；章节不存在 MUST 返回结构化错误而非回退全文

**MCP 接入**

- **FR-013**: MCP 客户端 MUST 从 Server 的工具清单与参数 schema 自动生成工具契约注册进注册表，MUST NOT 要求手工维护两份定义
- **FR-014**: MCP Server 不可达、超时或返回非法清单时，系统 MUST 降级（该来源工具不可见或标记失败），MUST NOT 影响内置工具的可用性与调用成功率
- **FR-015**: MCP 工具调用 MUST 经过与内置工具一致的执行管道（权限、校验、超时、重试口径相同），模型与上层无需感知工具来源差异

### Key Entities

- **ToolContract（工具契约）**: 名称、描述、入出参 schema、执行策略元数据（超时上限/最大重试/幂等标注/可并行标注/所需权限域）；同时驱动参数校验、模型工具面生成与文档
- **ToolExecutionRecord（执行记录）**: 一次调用的结果载体——成功负载或分类错误（校验/权限/超时/重试耗尽/未知）、重试次数、耗时、追踪标识、failed 标记；进入证据流
- **PermissionScopes（权限域）**: 请求持有的工具权限域集合，驱动可见面与执行前校验；与文档密级（visibility）严格分离（章程 V）
- **MCPToolSource（MCP 工具来源）**: 一个外部 MCP Server 连接及其工具清单；负责契约自动生成、命名空间隔离与健康降级

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 行为回归——引擎与权限改造合入后，既有 mock 化测试套件全绿，且同输入下 `hybrid_search` 单工具输出与阶段 2 基线一致（检索层 bit 级口径，clarify Q2）；端到端真实评测与悬置的 002-T045 合并执行，工具面扩展（doc_reader 上线）属预期行为变更、不适用端到端一致
- **SC-002**: 超时保障——对注入挂起/慢响应工具的调用，100% 在契约超时上限 + 容差内返回结构化结果，测试全程无无限等待
- **SC-003**: 瞬时故障自愈——对注入「首败后即成功」瞬时故障的工具调用，≥ 80% 无人工干预经自动重试成功返回
- **SC-004**: 非幂等零重发——非幂等工具遇超时/失败场景的自动重发次数为 0（执行记录可审计验证）
- **SC-005**: 越权全拒——对未授权工具的调用 100% 在执行前被结构化拒绝，且被拒工具不出现在该请求的规划面；空权限域请求 100% 得到空工具面与既有降级路径
- **SC-006**: 并行有效性——同一步 2 个独立调用（时延受控）的端到端耗时 ≤ 单调用耗时的 1.5 倍，结果顺序与计划一致
- **SC-007**: MCP 统一调度——≥ 1 个 MCP Server 工具在同一注册表被模型规划并调用成功，且其调用经过与内置工具相同的管道（执行记录口径一致）；MCP 来源整体故障时内置工具调用成功率保持 100%
- **SC-008**: 故障不中断（回归）——工具全类型失败（校验/权限/超时/重试耗尽/未知异常）仅产生 failed 标记证据，Agent 按既有收敛规则继续或输出完整降级答案，零半截输出

## Assumptions

- v1 模型可见工具面保持收敛为 `hybrid_search` + `doc_reader`（章程 I）；`sql_query` / `calculator` / `record_confirmation` 不在本阶段落地为内置工具，演示性计算工具经 MCP 接入即可满足「按场景加入」的架构验证
- 幂等验收口径取 docs/09 括号口径（非幂等工具不重试）：v1 工具面全为读工具（天然幂等），幂等键机制（FR-009）在首个写类工具接入时落地，存储选型届时立 ADR；本阶段不为此引入新基础设施组件（如 Redis）
- 权限域来源：本阶段由 API 层按请求注入 scopes（测试可控），JWT claims 完整落地属阶段 5 租户隔离范围；注入接口形状为 JWT 预留
- MCP Server 采用本地自建最小 Server（演示工具）；开发与 CI 测试使用 in-process mock session，不依赖真实外部服务（章程 VII）
- 阶段 2 遗留的真实 API 验收（002-T045、rerank 复测、001-T041/T044）仍悬置，不在本阶段范围；本阶段验收全部可在 mock/CI 层完成
- 既有 `Tool` Protocol / `Registry` / scope 收敛（阶段 2 落地的雏形）为本阶段演进基线，演进保持图与上层契约不变（docs/04 §4.1）
