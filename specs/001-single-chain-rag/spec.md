# Feature Specification: 单链路 RAG 问答（入库 → 检索 → 带引用回答）

**Feature Branch**: `001-single-chain-rag`

**Created**: 2026-09-02

**Status**: Draft

**Input**: User description: "文档入库 → 解析切分 → 索引 → 混合检索 → 重排 → 带引用回答，闭卷集 Recall@5 ≥ 0.8（docs/09 阶段 1）"

## Clarifications

### Session 2026-09-02

- Q: 本阶段的交付形态是什么？ → A: 最小 HTTP 服务——文档上传、处理状态查询、问答三个接口；前端原型接通真实链路；会话管理等完整 REST 留给后续阶段
- Q: 「同一文档版本」按什么口径判定？ → A: 内容哈希——上传时计算文档内容指纹，指纹相同即同版本（归并不重复入库），指纹不同即新版本
- Q: 三个接口在本阶段是否落鉴权？ → A: 落最小 JWT——签发脚本 + 校验中间件 + 租户上下文注入，与章程原则 V / ADR-009 一致
- Q: 阶段 1 是否记录运行档案？ → A: 记录本地最小运行档案——每次问答记录问题、命中条数、延迟、是否拒答、trace 编号；完整可观测栈留给后续阶段

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 提问获得带引用的回答 (Priority: P1)

保险业务/培训人员用自然语言提出条款问题（如「这款重疾险等待期多久？」），系统返回
一个明确、可直接引用给客户的答案，答案中的每个结论都带有引用标记；点开引用可以看到
被引用的条款原文（文档名、条款编号、被引原句），用于向客户或监管证明答案出处。

**Why this priority**: 这是产品的核心价值——可信、可溯源的条款问答；没有它其余一切无意义。

**Independent Test**: 在已入库的条款库上提问「这款重疾险等待期多久？」，收到带引用标记的
回答；点开任一引用可见条款原文且原句与答案结论一致。

**Acceptance Scenarios**:

1. **Given** 条款库已含重疾险条款, **When** 用户提问「这款重疾险等待期多久？」,
   **Then** 返回的答案明确给出等待期天数，并附至少 1 个引用标记
2. **Given** 答案带引用标记, **When** 用户点开引用,
   **Then** 显示对应条款原文（文档名、条款编号、原句），原句内容支撑答案结论
3. **Given** 提问含口语表述（如「买的保险多久才开始生效能赔」）, **When** 用户提问,
   **Then** 系统仍能命中「等待期」相关条款并正确作答

---

### User Story 2 - 管理员上传条款并自动可检索 (Priority: P1)

知识库管理员上传一份条款文档（纯文本为主，少量 PDF），系统自动完成解析、切分与索引；
上传后无需人工处理，文档内容即可被问答命中。重复上传同一文档不产生重复数据。

**Why this priority**: 没有入库就没有可检索的内容；与 US1 同为最小可用闭环的必要部分。

**Independent Test**: 上传一份条款，随后就其中独有的内容提问，能命中该条款并正确作答；
再次上传同一份，检索结果不出现重复引用。

**Acceptance Scenarios**:

1. **Given** 一份新条款文档, **When** 管理员上传,
   **Then** 系统在 5 分钟内完成入库，期间可查询到处理状态
2. **Given** 入库完成的条款, **When** 就其独有内容提问,
   **Then** 答案引用该条款原文
3. **Given** 同一份文档被重复上传, **When** 入库完成,
   **Then** 不产生重复的可检索条目（同一版本只保留一份）
4. **Given** 一份无法解析的损坏文档, **When** 管理员上传,
   **Then** 系统标记该文档处理失败并给出原因，可重新触发处理，不影响其他文档

---

### User Story 3 - 证据不足时拒答而非编造 (Priority: P2)

当条款库中没有与问题相关的内容时，系统明确回答「未找到相关条款」，并给出改进提问的
建议（如补充险种名称或条款术语），绝不编造答案。这保护业务人员不把错误信息传达给客户。

**Why this priority**: 可信度的底线；优先级低于核心问答，但必须在对外使用前具备。

**Independent Test**: 提问一个条款库中明显不存在的问题（如评测集 L4 拒答题），系统返回
拒答与建议而非编造内容。

**Acceptance Scenarios**:

1. **Given** 条款库中不存在相关内容, **When** 用户提问,
   **Then** 系统明确回答未找到相关条款，并附至少 1 条改进提问的建议
2. **Given** 检索结果与问题相关度极低, **When** 系统评估证据不足,
   **Then** 走拒答路径而不是产出低置信答案

---

### User Story 4 - 维护者运行检索质量评测 (Priority: P2)

项目维护者在闭卷评测集（kaihe 985 条问答 + 51 条拒答题）上运行离线评测，得到检索
命中率等指标报告与失败案例清单，作为本阶段验收与后续优化的标尺。

**Why this priority**: 验收与回归的依据；不阻塞功能开发，但验收前必须就绪。

**Independent Test**: 一条命令运行闭卷集评测，产出含 Recall@5 与失败案例的报告文件。

**Acceptance Scenarios**:

1. **Given** 就绪的闭卷评测集, **When** 维护者运行评测,
   **Then** 产出报告：整体与分难度（L0/L1/L3）的 Recall@5、拒答题拒答率、失败案例清单
2. **Given** 评测报告, **When** 检查失败案例,
   **Then** 每条失败案例可见「问题、期望命中条款、实际命中结果」，可直接归因

---

### Edge Cases

- 提问含错别字或同义说法（「免赔」vs「免赔额」）→ 仍能命中正确条款
- 同一产品存在多版本条款 → 引用必须标明文档名与版本，不混用版本内容作答
- 提问过短或过泛（「保险怎么赔」）→ 引导用户补充险种/场景，而非随机命中
- 文档为扫描件或空文件 → 解析失败路径，标记原因并支持重试
- 命中相似度处于阈值边缘 → 按拒答处理，宁可少答不可错答

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 系统 MUST 支持上传条款文档并自动完成解析、切分与索引，全程无需人工干预
- **FR-002**: 系统 MUST 展示每份文档的处理状态（处理中 / 已入库 / 失败）
- **FR-003**: 重复导入同一文档版本 MUST NOT 产生重复的可检索条目
- **FR-004**: 用户 MUST 能用自然语言提问并获得针对条款内容的回答
- **FR-005**: 口语化说法与条款专有名词（术语、数字、条款编号）MUST 都能命中相关条款
- **FR-006**: 每个非拒答回答 MUST 附带至少 1 个引用；引用 MUST 可展开为条款原文
  （文档名、版本、条款编号、被引原句）
- **FR-007**: 引用展示的原文 MUST 是条款原文片段本身，禁止改写、拼接或杜撰
- **FR-008**: 证据不足或相关度过低时，系统 MUST 走拒答路径并给出改进提问建议
- **FR-009**: 闭卷评测集的离线评测 MUST 可一键运行，产出指标报告与失败案例清单
- **FR-010**: 条款库为空或检索能力不可用时，系统 MUST 给出明确提示，MUST NOT 返回
  空白内容或未处理的错误信息
- **FR-011**: 系统 MUST 以最小 HTTP 服务交付，接口族为：文档上传、处理状态查询
  （含失败重试子操作）、问答；MUST NOT 在本阶段实现会话管理、多轮对话等后续阶段接口
- **FR-012**: 三个接口 MUST 校验自签 JWT，租户身份 MUST 只来自令牌 claims；
  无效或缺失令牌的请求 MUST 被拒绝并返回明确的未授权提示
- **FR-013**: 系统 MUST 为每次问答记录本地最小运行档案：问题、命中条数、延迟、
  是否拒答、trace 编号；MUST NOT 在本阶段引入完整可观测平台

### Key Entities *(include if feature involves data)*

- **条款文档**：标题、来源、内容指纹（同版本判定依据）、版本、密级（visibility）、
  处理状态、入库时间
- **条款块**：所属文档、章节编号、块类型（完整小节/段落/表格行）、父子关系
  （小块用于精确命中，完整小节用于展示原文）
- **问答引用**：文档、条款编号、被引原句、相关度分数

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 闭卷评测集（985 条问答）上，检索命中率 Recall@5 ≥ 0.8
- **SC-002**: L4 拒答题（51 条）上，系统正确拒答率 ≥ 90%
- **SC-003**: 简单事实类提问从提交到返回完整答案（含引用），95% 的请求在 8 秒内完成
- **SC-004**: 100% 的非拒答回答附带至少 1 个可展开原文的引用
- **SC-005**: 新上传条款从提交到可被检索命中，95% 在 5 分钟内完成
- **SC-006**: 抽样 20 条回答人工核对，引用原句与答案结论一致率 100%

## Assumptions

- 本阶段语料以纯文本条款为主（kaihe 102 份完整条款）；补采的真实 PDF（10~20 份）作为
  「文档解析能力」的独立验收子项，不阻塞核心问答链路
- 检索命中判定口径（clarify 后调整为**事实级**）：gold_answer 中的关键事实
  （天数/比例/金额等）出现在检索返回前 5 个结果之一的父块原文中即视为命中；
  标准原文 quote 子串包含作为参考口径一并输出。原 quote 严格口径在
  「52 份产品高度相似条款」语料下会漏判「其他产品的同类型条款」（2026-09-02 评审）
- 单租户演示环境；鉴权在本阶段以最小 JWT 落地（租户身份来自令牌 claims），
  权限域/密级授权与多租户隔离在后续阶段完成，数据字段从第一版即预留
- 本阶段为单问单答交互；多轮对话与 Agent 反思回环属后续阶段范围
- 评测集（闭卷 985+51、开卷 1060）已就绪（见 `data/README.md`），本阶段不新增标注
